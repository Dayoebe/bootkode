# BootKode architecture

BootKode is a Laravel 11 / Livewire 3 modular monolith. Blade and Alpine support server-rendered journeys; no new frontend framework is required.

## Responsibilities

- `routes/web.php` and `routes/auth.php`: stable named URL contracts, authentication, verification and role middleware. Laravel 11 middleware registration belongs in `bootstrap/app.php`; the old `app/Http/Kernel.php` is not the active registration mechanism.
- `app/Livewire/<domain>`: interactive form state, validation, authorization, pagination and orchestration. Check sensitive authorization on every request, including Livewire hydration.
- `app/Http/Controllers`: HTTP-only callbacks, auth, downloads and public verification. Gateway callbacks delegate verified financial mutations to services.
- `app/Services`: multi-record operations and reusable business rules. Transactions must not escape through early returns; financial operations lock current records before checking balances or statuses.
- `app/Models/<domain>`: persistence, relationships, casts and domain invariants. Core User has both a legacy `role` column and Spatie roles; use role APIs for authorization.
- `resources/views/layouts`: public, dashboard, blog, pages and exam shells. Exam has deliberate distraction-free behavior; do not turn administration into marketing.
- `resources/views/components`: static shared UI; Livewire is reserved for server interactions.
- `resources/css`: theme and semantic design tokens; `resources/js`: browser enhancement. Livewire owns Alpine.

## Data compatibility

`course_enrollments` stores enrollment/payment/completion metadata. Historical `course_user` stores learning pivot/progress. Existing CourseView reconciles historical enrollments. Maintain both when enrolling; do not delete historical tables as a cosmetic cleanup. `lesson_user`, LessonProgress and assessment UserProgress have distinct existing consumers; consolidate only with migration and behavioral coverage.

Wallet writes must atomically persist balance and ledger, reject nonpositive amounts and use row locks. Funding must verify gateway reference/status/amount/currency against a stored wallet-funding intent; transaction status, credit and receipt belong in one database transaction. Gateway webhook is public and HMAC-authenticated. Browser return URLs alone never establish payment success.

Public discovery only reads published, approved courses. Learning content still requires enrollment. Certificate verification codes remain stable. Server-side completion and role/ownership rules remain authoritative.

## Operational boundaries

MariaDB `bootkode_recovered` contains existing data and is not disposable. Tests use an explicitly dedicated database. Never run fresh/reset migrations against the working database. Schema changes require forward migrations. The certificate compatibility migration widens status storage, adds missing workflow fields and copies historical verification tokens/file paths only when the new fields are empty. The working database was backed up and the migration was validated on the dedicated test database before local application.

Provider credentials remain in environment/configuration, never Livewire public properties. Receipt, payout, newsletter and AI integrations need independent staging verification.

See `product-audit.md`, `design-system.md`, `refactor-roadmap.md` and `verification.md` for decisions and evidence.

## Course content acquisition

`CourseContentStudio` is a role-guarded Livewire entry point for importing licensed curriculum and generating AI drafts. `CourseContentSource` adapters own source-specific fetching, format parsing and licence checks; `CourseImportService` owns source identity, duplicate/revision handling and draft persistence. The initial GitHub adapter accepts only the verified freeCodeCamp curriculum block path and fixed GitHub hosts. `AiCourseGenerationService` uses `AiManager`, persists blueprint/module stages, enforces a separate usage limit and delegates course/lesson/assessment writes to the existing `CourseGenerationService`.

`course_content_runs` is processing/attribution metadata, not a second course or learning system. The additive migration links runs to the normal Course model and retains source revision, licence, status and review flags. The queue jobs are retry-safe and do not keep database transactions open during network calls. Course and run completion writes are atomic after external retrieval/generation. Every resulting course remains a draft; `Course::publiclyAvailable()` and existing course approval/enrollment boundaries remain authoritative.

See [course-content-system.md](./course-content-system.md) for supported formats, license requirements, configuration, commands, queue setup, retries and limitations.

## Saved certificate designs and career applications

`CertificateTemplate` stores validated design settings, not arbitrary HTML or Blade. `CertificateService` owns writes/default changes/deletion; only academy/super administrators manage designs and only super administrators assign a default. A nullable unique `default_slot` enforces one default in storage. The selected design is copied into existing certificate metadata at approval. Rendering uses that snapshot; editing or deleting the source design never restyles an issued record. Records predating snapshots retain the historical design and tokens/files. Preview HTML is isolated in a sandboxed iframe with explicit non-issued placeholders; fonts are restricted to those available to the PDF renderer.

`JobApplicationService` resolves currently public/internal/open applications and locks the career job before creating an application and updating its count in one transaction. A retry returns the original application. Failed persistence cleans up a newly stored résumé. New résumés use the private local disk; the download controller checks applicant ownership or administrator roles. Legacy public paths remain readable through the guarded controller, but already-public historical assets need an independent backup/move procedure before claiming they are private.

The career compatibility migration validates both tables for unmatched records before any constraint DDL. Both application/save foreign keys target `job_portal`, never the unrelated Laravel queue table. Community moderation checks authorization inside every read/mutation boundary as well as rendering. Code solutions are pending and ungraded until a real review supplies a result; submission alone does not create a score.

## Marketplace, institutional membership, and mentorship boundaries

Marketplace wallet checkout has one boundary in `MarketplaceService::checkoutWallet`, shared by Livewire and the legacy HTTP controller. It locks the customer and current wallet, resolves published items/prices/commission on the server, and binds each paid order to its matching debit. Vendor/platform credits, order state and invoice share the transaction. A session checkout UUID returns existing customer orders on replay. Commission uses integer minor units with the vendor receiving the remainder. Settlement wallets must match the order currency. Full wallet refunds reverse actual credited wallets and restore the customer in the same transaction; insufficient recovery funds roll everything back. Card settlement and partial/external refunds are not implemented by this wallet boundary. Historical paid orders without funding evidence are retained, but cannot mint another payout through it.

Paid marketplace files now use private local storage and `marketplace.order.download` checks the paid customer's ownership. Public item serialization hides file paths and public reviews load only approved records. Legacy public paths retain guarded-download compatibility; already-public assets still require a separately backed-up move. Listing uploads persist with category assignment, preserve existing attachments on edit, and clean up new uploads on failed persistence. The historical JSON `categories` column remains untouched; `itemCategories` is the unambiguous pivot relation for reads.

Institutional `admin` and `instructor` are membership roles, not global platform roles. New institution accounts remain global students. Invitation GET requires sign-in and only reviews; CSRF-protected POST rechecks the target account/email, pending state, expiry and capacity under locks. Accepting does not log in the recipient, verify email, or promote a global role. Existing global roles are preserved and require a separate administrator review if previously over-granted. Institutional administrators have a membership-scoped portal; platform staff operate cross-institution licensing/cohorts/imports. Enrollment rechecks `Course::publiclyAvailable()` in services and queued CSV processing. Cohort assignments validate active members of the actual institution before writes.

Mentorship reads/actions re-resolve actual participant ownership. Mentor-only parent and nested components check roles on every request. Completion locks the persisted session; paid completion debits the mentee's existing NGN wallet and credits the mentor atomically, with transaction IDs in metadata. Repeated/stale completion cannot repeat payment or session counters. Insufficient funds roll back completion. Historical paid flags are preserved. New legacy-session attachments use private storage; historical public files are not relocated by this code change. Unpublished mentor resources have explicit unavailable states.

Search defaults to Scout's collection engine when Algolia credentials are absent. An explicitly configured driver remains authoritative; configured Algolia still needs working credentials and independent acceptance.

## Recorded learning, rewards and CBT attempts — 22 October 2026

Both historical personal analytics routes now share one Livewire implementation and `LearningAnalyticsService`. Owner identity comes from authentication; a supplied different user ID is refused. The service merges canonical and legacy enrollments without double counting, deduplicates lesson completion records, separates recorded session minutes from saved lesson study time and aggregates complete graded attempts. It never substitutes estimated lesson duration for measured time. Finished CBT result snapshots take precedence over recalculating history from edited questions. Personal goals persist in existing `learning_goals`; CSV export and optional visible polling use the same scoped records. The dashboard bundle owns chart initialization/destruction.

`GamificationService` now orchestrates actual persisted completion evidence, daily claims and supported reward delivery. Gamification mutations serialize through the user and fresh data row, reject nonpositive movements and persist balances with their ledger records. Daily rewards use the existing transaction history as their once-per-day evidence; quest completion is saved before paying its reward. Consecutive learning streaks and fractional energy regeneration are corrected. Supported energy redemption debits coins/gems and records delivery atomically; replay and failed inventory writes cannot repeat or partially spend currency. The canonical oldest gamification row is used without deleting possible historical duplicates. No migration or record consolidation was performed.

Gamification GET routes mount the real shared Livewire component. The leaderboard queries current active accounts with explicit metadata consent and a public profile, projecting only name/rank/points/level. Consent withdrawal takes effect without a shared user-model cache. Unsupported games, special-event awards, reviewed learning paths, cosmetic delivery and achievement broadcasts report their unavailable state; random game results and invented delivery are removed. Existing badges, scores, purchases and virtual currency remain stored.

`CbtAttemptService` rechecks enrollment/owner/platform access for course-linked exams; standalone CBT remains available under its existing authenticated contract. It records a real `learning_sessions` attempt under a user lock, reuses active attempts across reloads, validates answer ownership/options, saves answers before final submission and enforces the server deadline. A completed attempt returns its existing result. Questions, order, start state and attempt identifiers are locked in Livewire. Public question payloads exclude answer keys. Grading snapshots stay in private session metadata, which is hidden from model serialization; later question edits cannot change the attempt's marking rules. Grades, elapsed time, completion metadata and eligible rewards persist transactionally. History guards also cover assessment answers and learning sessions. No schema migration is required.


## Written assessment review and immutable session clocks

`StudentAssessmentTaker` is the same component in the embedded lesson panel and named `lesson.assessments` workspace. It resolves assessments through the actual lesson, checks account/enrollment/published lesson/section eligibility on requests and delegates all attempt writes to `CbtAttemptService`. Client state contains safe question projections and owned drafts; private keys, rubric guidance, original marks, pass threshold and review audit metadata remain in the persisted session. The focused CBT player retains its auto-graded format contract; lesson mode additionally supports text responses and multiple selections. Unsupported interaction formats are refused before starting a new attempt.

Written submission creates an answer row for every question, including unanswered work, and records `pending_review=true`, `passed=false` and null final points/percentage. `AssessmentReviewService` resolves the actual course owner/platform role, rejects self-grading, serializes on the learner and attempt, scopes the answer to that exact submitted attempt and bounds the score by the saved rubric. Marks, reviewer/time/feedback, private review log, final snapshot and eligible reward commit together. Partial review never publishes a final result. Repeated identical marking returns the recorded result; changed marks require a separate formal correction process. No outbound result email or invented notification is implied.

`Assessment::getStudentResults` prefers recorded snapshots over current question definitions. Legacy unreviewed written work is conservatively pending. Result views strip answer/question model graphs from public properties. `AssessmentResultService` projects owned submitted responses using the original question/option snapshot, preserving answer review without publishing grading keys. New lesson completion, progress flags, lesson rewards and certificate requests read actual reviewed results; caller-provided pass/completion state cannot issue a credential. Existing issued credentials and historical records remain intact. CBT management scope is checked on both request hydration and each resource action; course reassignment/deletion cannot discard recorded attempts.

The start-time compatibility migration removes MariaDB's implicit timestamp update behavior with an explicit column default. It performs no historical timestamp repair and its rollback intentionally does not reintroduce that rule. Before applying it, retain a private schema/record backup and verify it against a dedicated database. The verification report records the actual working-table state and preservation check.

## Structured questions and scoped authoring

`StructuredQuestionService` defines the supported structured format boundary. Matching/drag-drop options contain `version: 1`, parallel `prompts` and `choices` arrays; ordering contains `version: 1` and `items`. Authoring accepts 2–12 complete unique pairs/items. Correct original positions stay in `correct_answers`. Model casts serialize arrays once. Legacy double-encoded choice data can still be read; there is no bulk rewrite of historical definitions.

`CbtAttemptService` prepares public question projections and private grading metadata together. Structured choices are shuffled, and their display-to-original permutation lives only in private `grading.option_map`, never in a public question map. Drafts use display positions. Submission validates position/shape, maps to original positions and grades the exact sequence/pairs atomically. Partial matching drafts are allowed but incomplete, repeated or incorrect matches receive zero credit. An ordering response must be a complete permutation. A displayed default sequence is unsubmitted until the learner moves/saves/submits an actual response; untouched controls record no answer. Original target/choice labels, keys, points and pass thresholds remain frozen for the attempt.

`AssessmentResultService` projects only the learner's submitted structured responses using those original labels and private maps. New automatic structured marks have real grading timestamps; mixed written work remains pending until manual review is complete. The legacy model helpers preserve exact order/set semantics and refuse automatic marking of written responses. Existing rows are not automatically regraded.

`AssessmentAuthoringService` reuses `CourseAuthoringAccess` for actual ownership and centralizes complete-list ordering and atomic copying. Lesson/assessment locks serialize those changes; copies include definitions only. The existing lesson assessment manager also serves the contextual `lesson.assessments.manage` route. Resource identifiers and loaded definitions are locked in Livewire, and action queries resolve actual server records. Maximum attempt settings persist through the existing `max_attempts` field. Unsupported immediate-result switches were removed from the interface rather than claiming they were saved.

Keyboard alternatives use ordinary labelled controls. A small `bootkode-list-moved` handler in the existing dashboard bundle restores focus to the moved item's enabled control after Livewire changes the DOM. Dragging is a progressive enhancement over the same selection fields and server validation, not a separate submission mechanism. No dependency, frontend runtime or database migration is added.

## Reviewed marks, corrections and owner review requests — 22 October 2026

`AssessmentReviewService` remains the write boundary for initial marking and explicit corrections. New correction and review-request events append to the existing hidden `learning_sessions.metadata`; they do not require a schema migration or backfill. The service locks the learner, attempt and actual answer rows in that order, checks the current course owner/platform reviewer and refuses self-review. Only finalized written answers with a complete original grading snapshot can be corrected or appealed. Automatic questions, pending results, cross-attempt answers and unsupported historical records cannot use this workflow.

A correction retains the previous points, feedback, grader/time and complete result snapshot, plus the replacement mark/result, reviewer, reason, operation UUID and time. The current answer and result publish in the same transaction as that history. Original question definitions, pass threshold, submitted text, initial review log and session clock remain authoritative. A server-issued revision hashes the actual marks and private review state; a stale decision is refused. Exact operation replays return the recorded outcome, while reuse with changed content is refused. Review context and operation identifiers are locked Livewire properties.

The owner may request review of a finalized written mark from either existing result surface. Retained personal results remain available after enrollment ends; a new request still resolves only the authenticated owner's assessment, attempt and answer. One request is allowed per answer correction version; exact retries do not reopen a resolved request. The reason/status/decision remain in history. A correction closes that answer's open request, while an explicit reasoned decision may uphold its existing mark. `open_mark_reviews` is a server-maintained projection for the scoped staff queue. Staff can filter pending, requested-review and finalized submissions.

Corrections recalculate future passing/progress/credential eligibility using the original snapshot. They neither mint nor claw back rewards, remove completion records, nor alter issued/revoked credential statuses, tokens or files. Any separate institutional remediation of an already issued credential requires its existing authorized process. Learners receive only submitted responses, mark changes and review reasons/decisions; private keys, rubric guidance, grader identifiers, full audit result snapshots and operation/revision data stay server-side. No email or notification delivery is claimed; decisions are visible in the existing personal results.

Draft removal revokes the recorded URL; submitted attempts cannot be changed. Answer records reference file IDs; file-only work stays pending manual review. Expiry records existing work without inventing required files or marks.

`assessment.submission-file` requires authentication and verification. Draft downloads are owner-only; submitted downloads allow the learner or the currently authorized course/platform reviewer. No public path, grading guidance, execution, archive extraction or automated file grading is exposed. Retained owner downloads remain available after enrollment ends.
